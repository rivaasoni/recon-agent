How it works

  1. Match what's obvious. Same reference, same amount, dates within a window — strictly one-to-one, so a duplicate posting can't hide inside a match.
  2. Investigate the rest. The agent queries the bank and ledger tables and searches supporting documents (invoices, wire confirmations, the bank's fee schedule) through a read-only tool server.
  3. Propose, never post. It drafts a balanced double-entry and records it as pending. No tool exists that could write to a ledger.
  4. A human decides. A reviewer sees the case, the entry, the evidence and the full reasoning before approving or rejecting.
  5. Grade every run. The data is generated with an answer key the agent never sees, and each run is scored on the classification and the entry's effect on cash.

    How the grading works

    1. The generator seeds exceptions of known type and writes an answer key to a folder that is never loaded into the warehouse the agent can query — a test enforces that.
    2. The answer key and the agent's work use unrelated ID spaces, so nothing links them by accident. The grader joins them on the bank and ledger row IDs they share.
    3. A correct label with the wrong amount counts as a failure: "fully correct" needs both.
    4. Which expense or payable account to use is a judgement call, so the offset account is reported but never fails a case.

    How to read these numbers

    • Small sample. 16 cases, 2–3 per type. One mistake moves a type's accuracy by 33–50%, so per-type figures point at what to investigate; they are not reliable rates.
    • One run. Model output varies between runs; measuring stability needs repeats.
    • Synthetic, tidy data. Every exception has decisive evidence reachable through the tools. Real statements bring partial payments, batched deposits and missing paperwork — none are represented here.
    • The rules did the easy work first. Deterministic matching paired 114 of 125 bank lines, so the agent only saw genuine exceptions.
