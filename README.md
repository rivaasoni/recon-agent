# Agentic Reconciliation Exceptions Assistant

> ⚠️ **All data in this project is synthetic.** No real company, bank, customer or
> account information is used anywhere. The data is generated by a script in this
> repo and is deliberately obviously fake.

An AI agent that investigates **bank reconciliation exceptions**, classifies them,
proposes a correcting journal entry, and **waits for a human to approve it**.

### ▶ [Live demo: recon-agent-zeta.vercel.app](https://recon-agent-zeta.vercel.app)

All 16 exceptions with the agent's full reasoning traces and the evaluation results.
The demo is static and read-only: it serves pre-computed results and never calls a model.

Deterministic rules clear the easy matches between a bank statement and a general
ledger. Only what's left over — the genuine exceptions — reaches the agent, which
investigates with tools, cites its evidence, and drafts a fix. Every step is logged,
every proposal is graded against ground truth, and **nothing is ever posted to a ledger**.

## Results

One month of synthetic data: 125 bank lines, 125 ledger entries, 16 seeded exceptions
across 6 types.

| | Result |
|---|---|
| **Matched by rules** | **114 of 125 bank lines** — 91.2% by count, 95.7% by value |
| **Exceptions raised** | 16 cases, worth **$84,583.56**, with no false alarms |
| **Agent classification accuracy** | **16/16 (100%)** |
| **Agent fix accuracy** | **16/16** — every proposed entry matched the correct cash adjustment to the cent |
| **Cost** | **$1.69 per run**, $0.106 per case |
| **Speed** | 32s median per case (89 tool calls across the run) |
| **Reliability** | 16/16 investigations completed; 3 cases hit a network failure mid-run and were recovered by resuming |

Full report, including the confusion matrix and the caveats behind that 100%:
**[docs/evals/report-run-20260921-215515.md](docs/evals/report-run-20260921-215515.md)**

A perfect score on 16 synthetic cases is not a claim that the problem is solved.

## The problem

Every month, a company compares its **bank statement** (what the bank says happened)
with its **general ledger** (what its accountants recorded). The two should agree.
They never quite do.

Most lines match trivially: same invoice number, same amount, a day or two apart.
The rest are **exceptions**, and they're where the time goes. Each one has to be
investigated by hand: pull the invoice, check the wire confirmation, work out whether
it's a bank fee nobody booked, a payment recorded twice, a currency conversion at a
different rate, or simply money still in transit. Finance teams spend days a month on
this, and the answer usually sits in a document somebody has to go and find.

The six exception types this project handles:

| Type | What happened | Right fix |
|---|---|---|
| **Timing difference** | Booked at month end, clears the bank next month | **No entry** — it fixes itself |
| **Duplicate** | The same bill posted twice | Reverse the extra posting |
| **Bank fee** | The bank charged a fee nobody recorded | Book the fee |
| **FX difference** | Booked at the invoice rate, settled at a different one | Book the FX gain/loss |
| **Missing ledger entry** | Money moved; nobody recorded it | Record the transaction |
| **Amount mismatch** | Recorded with two digits transposed | Correct the amount |

Notice that one of the six correct answers is **"do nothing"**. An assistant that
"fixes" a timing difference has made things worse, so knowing when *not* to act is
part of the job — and part of the evaluation.

## Requirements

**Functional**

1. Match bank lines to ledger entries automatically where the evidence is unambiguous.
2. Present everything else as a case, with the facts a reviewer needs.
3. For each case: classify it, explain the reasoning, cite the evidence, and draft the correcting entry.
4. Let a human approve or reject, with the agent's full reasoning visible.
5. Hand approved entries to a person to post, and report on the whole process.

**Non-functional (the constraints that shaped the design)**

1. **The agent can never write to the ledger.** Enforced by the tools available, not by asking it nicely.
2. **Every decision is auditable**: which tools ran, what they returned, what it cost.
3. **Accuracy is measured**, not asserted — graded against ground truth the agent cannot see.
4. **Cost is visible per case**, because an agent that costs more than the work it saves is not a solution.
5. **No real data, ever.** Everything is generated.

## User stories

> **As a staff accountant**, I want the easy matches cleared automatically, so that I
> only spend time on the items that actually need judgment.

> **As a staff accountant**, I want each exception to arrive with a suggested
> classification, a draft journal entry and the evidence behind it, so that I can
> approve or reject in seconds instead of re-investigating from scratch.

> **As a financial controller**, I want to see the agent's reasoning before anything is
> approved, and a record of who approved what, so that the process survives an audit.

> **As the finance systems owner**, I want to know how accurate the agent is by
> exception type, and what a run costs, so that I can decide where it's safe to use.

## Architecture

```
Synthetic data ──▶ DuckDB + dbt ──▶ Rule-based matching ──▶ 16 exception cases
                                                                    │
                                              MCP server (read-only tools)
                                                                    │
                                          Claude Opus 5 agent loop (traced)
                                                                    │
                                       proposals (pending) + reasoning traces
                                                    │                   │
                                     Streamlit review (approve/reject)   │
                                                    │                   │
                            approved entries CSV ◀──┘                   ▼
                            (a PERSON posts these)         eval vs answer key
                                                           + analytics marts → Power BI
```

**Full diagram, trust boundaries and design rationale: [docs/architecture.md](docs/architecture.md)**
**2-minute walkthrough script: [docs/demo-script.md](docs/demo-script.md)**

The three decisions worth pointing out:

**1. Rules first, agent second.** 114 of 125 lines match on reference, amount and a
date window. Deterministic SQL does that for free and identically every time. The LLM
is reserved for the 16 cases where rules run out — which is also why a run costs $1.69
rather than $15.

**2. The agent physically cannot write.** Its tools open DuckDB `read_only=True` and
every query is parameterised, so the model never writes SQL. There is no "post entry"
tool, and a test locks the tool list so one can't be added quietly. Its only output is
a proposal marked `pending_human_approval` in a separate file.

**3. Ground truth never enters the warehouse.** The answer key is generated with the
data, stored outside the database, and used only by the grader — which joins it to the
agent's work through shared transaction IDs, because the two ID spaces were deliberately
kept unrelated. A test proves the answer key never reaches the database the agent queries.

## How it works

| Stage | What happens |
|---|---|
| **Generate** | One month of bank + ledger data from a seeded generator, with 16 exceptions of known type, 32 supporting documents (including decoys), and an answer key |
| **Load & model** | Raw files land untouched in DuckDB; dbt builds typed staging models and business-ready `cleaned` models, with 80+ data tests |
| **Match** | Reference + amount + date window, strictly one-to-one. First-in-first-out, so a duplicate posting is left over rather than silently matched |
| **Serve tools** | An MCP server exposes 7 read-only lookups plus `propose_journal_entry`, which validates double-entry (debits = credits, whole cents, real accounts) |
| **Investigate** | The agent works each case with Claude Opus 5 and the Anthropic Tool Runner; every step, tool call, token and second is written to a trace |
| **Review** | A Streamlit app shows the case, the proposed entry, the evidence and the full reasoning trace, with Approve / Reject and an append-only decision log |
| **Grade** | The eval harness scores classification *and* the proposed entry's effect on cash, with a confusion matrix and failure list |
| **Report** | dbt analytics marts (match rate, breaks by type, open value, agent cost) exported as Parquet/CSV for Power BI |

### What a real investigation looks like

CASE-006, resolved by the agent in 5 steps for $0.15:

1. Read the case: both sides exist, reference `BILL-5059`, difference **−208.68**, ledger currency **GBP**
2. Fetched the bank row, the ledger row and the supporting documents **in parallel**
3. Found the vendor bill (GBP 9,400.31) and the bank's wire confirmation (**rate 1.3022**), against the ledger's **1.2800**
4. Checked that the $35 wire fee mentioned in the confirmation belonged to a *different* case, and excluded it
5. Proposed: debit `7100 FX Gain/Loss` 208.68, credit `1000 Cash - Operating` 208.68 — matching the answer key exactly

It also ruled out `duplicate` and `amount_mismatch` explicitly, and noted the related
fee cases for a human to pick up.

## Limitations

The honest list. Each is a real constraint of this project, not a hypothetical.

- **Synthetic, tidy data.** Every exception has decisive evidence reachable through the
  tools. Real statements bring partial payments, batched deposits (one bank line, five
  invoices), missing paperwork and genuinely ambiguous cases. None are represented here.
- **Small eval set.** 16 cases, 2–3 per type. One mistake would move a type's accuracy by
  33–50%, so per-type numbers indicate what to investigate; they are not reliable rates.
- **One run, one month, one model.** LLM output varies between runs; measuring stability
  needs repeats. The data is a single August, single bank account, USD with EUR/GBP bills.
- **The matcher is one strict rule.** It works because the data always carries a clean
  reference. Real data needs fuzzy matching, and a looser rule risks false matches — which
  are worse than missed ones, because they *hide* exceptions.
- **Cost doesn't track value.** The agent spent $0.38 investigating $115 of bank fees and
  $0.26 on $36.5k of duplicates. Effort follows investigation difficulty, not materiality.
- **Approval is a demo boundary.** Approved entries are exported as CSV for a person to
  import. There is no write-back to an accounting system, by design.

## Next steps

1. **Harder eval cases**: partial payments, batched deposits, missing documents and
   deliberately ambiguous exceptions, plus repeat runs to measure stability.
2. **Route by value.** Send small, pattern-matched exceptions (fees that match the published
   fee schedule) to a rule, and reserve the agent for valuable or ambiguous cases.
3. **Model comparison.** Same eval on a cheaper model to quantify the accuracy/cost trade-off.
4. **Learn from rejections.** Reviewer rejection notes are already captured; they are the
   natural input for prompt improvements and a regression set.
5. **Multi-month and multi-account**, with aging on open breaks.

## Run it yourself

Needs Python 3.13 (dbt does not support 3.14 yet). Everything except the agent runs
without an API key.

```bash
git clone <this-repo-url> && cd recon-agent
python3.13 -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env            # paste your Anthropic API key (only needed for the agent)

pytest                          # 188 tests, no API key needed

python -m recon.pipeline.run    # generate data -> load DuckDB -> dbt build (models + tests)
python -m recon.matching.evaluate   # score the matcher against ground truth
```

Then, with an API key (**costs about $1.70** on Claude Opus 5):

```bash
python -m recon.agent.hello_claude            # check the key works (<$0.01)
python -m recon.agent.run_case CASE-006       # one case, printing every step (~$0.15)
python -m recon.agent.run_all --max-cost 6    # all 16 cases
python -m recon.evals.report                  # grade the run and write the report

streamlit run app/review_app.py               # review and approve (free)
python -m recon.pipeline.refresh_analytics    # rebuild metrics + export for Power BI
```

## Tech stack

| Layer | Choice | Why |
|---|---|---|
| Warehouse | **DuckDB** | Real SQL, one file, no server to run |
| Transformations | **dbt-duckdb** | Version-controlled, tested SQL with lineage |
| Agent | **Anthropic SDK Tool Runner** (`claude-opus-5`) | The agent loop stays visible and explainable, unlike a heavier framework |
| Tools | **Custom MCP server** | Tools written once work with any MCP client, and the server is the security boundary |
| Review UI | **Streamlit** | The approve/reject app, in one Python file. It writes decisions, so it runs where the data is — not on a public URL |
| Public demo | **Static HTML/CSS/JS on Vercel** | A read-only view of results already produced. No build step, no backend, and no way to call a model — so the public site can't cost anything or touch the API key |
| Tests | **pytest** | 188 tests, including a scripted fake Claude that exercises the whole agent loop for $0 |
| BI | **Power BI** | Reads the exported Parquet/CSV marts |

## Engineering notes

A few decisions that came from problems rather than plans:

- **The agent loop is fully tested without the API.** A fake Claude follows a script while
  the MCP server, tools, database, proposals and traces stay real — so tool errors,
  mid-run API failures, budget caps and resume logic are tested deterministically in
  under a second.
- **A real network failure shaped the batch runner.** Three of 16 cases failed mid-run.
  Error isolation kept the other 13, failures cost nothing (no completed steps), and
  `--resume` finished the run for $0.38 instead of repeating $1.69.
- **Tests that can't fail are worthless.** The check that the answer key never reaches the
  warehouse was rewritten after a sabotage test proved the first version could never fail.
- **Fixture drift is real.** The hand-built test warehouse fell behind the dbt models and
  broke the UI tests; a test now compares their columns.
- **Duplicates drove the matching design.** One payment with two identical ledger postings
  would let a naive join mark both as matched, hiding the duplicate. Matching is strictly
  one-to-one, mutual-best, FIFO — so the later posting surfaces as the exception.
